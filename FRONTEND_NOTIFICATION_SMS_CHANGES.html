Notification & SMS Changes

Everything a frontend developer needs after the notification refinement release. Two areas are affected: a new admin settings screen, and the notification types your customer UI switches on.

Nothing you already call has changed shape. GET /api/v1/notifications and POST /api/v1/notifications/{id}/read keep the same request, response, pagination and fields. What changed is which type values arrive, plus two brand-new admin endpoints.

What changed (TL;DR)

1. One notification type became three

The shipment lifecycle used to produce a single generic shipment_sent notification for two completely different situations. It is now split, and pickup — which previously produced no notification at all — has one of its own.

// Old — one type covered postal handoff AND local dispatch
shipment_sent

// New — one type per real-world moment
shipment_ready_for_pickup   // pickup order is waiting at the counter (NEW moment — nothing existed before)
shipment_handed_to_post     // postal parcel given to the carrier, has a tracking code
shipment_out_for_delivery   // courier is on the road with the order
Do not delete your shipment_sent branch. Historical notification rows were never rewritten, so a customer who ordered before this release still has shipment_sent notifications in their list and will see them forever. The backend no longer creates them — but your UI must still render them. Treat it as a legacy alias meaning "your order shipped".

2. The admin paid-order SMS became configurable

Every admin still receives the in-app admin_order_paid notification exactly as before — that is not configurable and you should not build a switch for it. What is new is that only selected admins additionally get an SMS, and there is now an admin screen to pick them.

Order paid
  ├─ customer    → in-app + SMS  (unchanged)
  ├─ all admins  → in-app  (unchanged)
  └─ selected admins → SMS  new

Suggested branching shape. Group the new shipment types with the legacy one so a single UI concept ("your order is on its way") does not fragment:

switch (notification.type) {
  case 'shipment_ready_for_pickup':
    // "Ready for collection" — show the store/pickup instructions
    break;

  case 'shipment_handed_to_post':
    // "Handed to the postal service" — show data.tracking_code if present
    break;

  case 'shipment_out_for_delivery':
    // "Out for delivery" — remind the customer they will be asked
    // for the code they received by SMS. Never try to read the code here.
    break;

  case 'shipment_sent':
    // LEGACY: pre-split rows only. Generic "your order shipped" copy.
    // May carry data.tracking_code. Keep this branch indefinitely.
    break;

  default:
    // Always keep a fallback: historical rows may carry types you do
    // not know about, and new ones can be added server-side.
}

Admin UI — paid-order SMS recipients

A settings screen that answers one question: which administrators should get a text message when an order is paid? It does not control the in-app notification, which every admin always receives.

Authentication & permission

  • Sanctum bearer token, same as every other admin endpoint (Authorization: Bearer <token>).
  • Permission required on both endpoints: notification.admin-sms-recipients.manage.
  • Seeded to the admin role only. The customer role does not have it.
  • GET /api/v1/me exposes the caller's permissions — use it to decide whether to render the menu entry at all, rather than letting the user walk into a 403.

GET /api/v1/admin/notifications/admin-order-paid-sms-recipients

Returns every administrator, each flagged with whether they are currently selected. There is no separate "list all admins" call to make — this one response is the whole picker.

The list is not paginated — there is no meta/links envelope, just data. Rows are ordered by user_id ascending, which is stable across calls.

An admin with phone: null can still be selected. The backend accepts it and simply skips the SMS at send time — nothing errors and the order still completes normally. Show a warning next to such a row (for example "no phone number — will not receive SMS") rather than disabling the checkbox, so the operator understands why nothing arrives.

PUT /api/v1/admin/notifications/admin-order-paid-sms-recipients

Replaces the entire selection. This is a set operation, not a toggle: whatever you send becomes the complete list of selected admins, and anyone omitted is deselected.

Request body

{
  "user_ids": [4, 12, 19]
}
  • user_ids is required as a key but may be an empty array.
  • [] is valid and meaningful: it deselects everybody. Do not special-case it into "skip the request".
  • Values must be integers ≥ 1 and distinct.
  • Every id must belong to an administrator. A customer id is rejected even though the user exists.
  • Sending the same list twice is a no-op — safe to retry, and safe to fire on every checkbox change if you prefer that to an explicit Save button.

Response · 200

Identical shape to GET — the full refreshed roster. Use it to re-render directly; there is no need for a follow-up GET.

{
  "data": [
    { "user_id": 4,  "name": "Ali",  "last_name": "Rezaei", "phone": "09121234567", "enabled": true  },
    { "user_id": 7,  "name": "Sara", "last_name": null,     "phone": "09351112233", "enabled": false },
    { "user_id": 12, "name": "Reza", "last_name": "Karimi", "phone": null,          "enabled": true  }
  ]
}

Error responses

StatusWhenHow to handle
401 No token, or an expired one. Applies to both endpoints. Normal re-authentication flow.
403 Authenticated but lacking notification.admin-sms-recipients.manage. Hide the screen for these users. Note that PUT returns 403 before validating the body, so a malformed body from an unauthorized caller is still a 403, never a 422.
422 Missing user_ids, a non-array, non-integer entries, duplicates, or an id that is not an admin. Standard Laravel validation envelope. Nothing was saved — the whole request is rejected, not the valid half.
429 Rate limit (api limiter, 60/min per user). Respect Retry-After. Debounce if you save on every checkbox change.

422 — a non-admin id

The error key is indexed by position in the array you sent, so you can highlight the exact row:

{
  "message": "User [7] is not an administrator.",
  "errors": {
    "user_ids.1": ["User [7] is not an administrator."]
  }
}

422 — a missing key

{
  "message": "The user ids field must be present.",
  "errors": {
    "user_ids": ["The user ids field must be present."]
  }
}

Rendering the picker

  1. GET the endpoint once when the screen opens. You now have every admin and their state.
  2. Render one row per admin: display name (name + last_name, falling back to phone, falling back to #user_id), the phone, and a checkbox bound to enabled.
  3. On save, collect the user_id of every checked row into user_ids and PUT it.
  4. Re-render from the PUT response. If it returns 422, keep the operator's local selection and surface the field error — nothing was persisted.

Copy worth putting on the screen, because it is the part operators get wrong: "All administrators receive the in-app notification for every paid order. The administrators selected here also receive an SMS."

Two defensive rules for the notification list. (1) Always keep a default branch — historical rows carry types that are no longer produced, and new types can be added server-side without a frontend release. Falling back to title + message, which every row always has, is a perfectly good default renderer. (2) Treat every data field as optional. tracking_code is omitted when no tracking number was recorded, and older rows may lack order_public_code.

Which identifier to show the customer: always order_public_code (for example bdo-Q8M2XC) — it is what support asks for. order_id is the internal numeric id and is there for deep-linking to your own order route.

Pickup flow

pending → preparing → ready_for_pickup → picked_up

Entering ready_for_pickup now notifies the customer in-app and by SMS. Before this release, a pickup customer was told nothing and had to guess when to come.

  • Notification type: shipment_ready_for_pickup.
  • SMS: contains the order public code.
  • What to show: a clear "ready for collection" state on the order, with the store's pickup instructions and opening hours if you have them.
  • picked_up sends nothing. The customer is standing at the counter when it happens — do not expect a second notification, and do not build a UI that waits for one. Reflect collection from the order/shipment status instead.

Postal flow

pending → preparing → ready_for_post → handed_to_post
  • Notification type: shipment_handed_to_post, carrying data.tracking_code.
  • SMS: contains the order public code and the tracking code.
  • What to show: the tracking number, ideally copyable, plus a link to the carrier's tracking page if you have one.
handed_to_post is the end of the road for postal tracking. The shop does not track the carrier's own lifecycle, so there is no in_transit, no postal out_for_delivery, and no postal delivered notification. Do not build a progress bar that promises those steps — after handoff, the tracking number is the customer's only source of further updates.

Local delivery flow

The delivery-person feature is unchanged in behaviour. Only the notification wrapping around it changed.

admin assigns a driver → admin dispatches
→ out_for_delivery  (customer gets ONE SMS: order code + verification code)
→ customer reads the code to the driver on arrival
→ driver (or an admin) submits that code
→ delivered
  • Notification type: shipment_out_for_delivery — one in-app row.
  • SMS: exactly one message, containing the order public code and the verification code. There is no separate "your order shipped" SMS followed by a second code SMS; that would have been two texts about one event.
  • What to show: an "out for delivery" state, plus a reminder that the customer will be asked for the code they received by SMS, and that they should only give it to the person actually handing over the order.

Delivery verification code — the rules

The verification code is SMS-only and is never returned by any API.
  • It is not in the notification data payload.
  • It is not in the order, shipment, admin, or driver responses.
  • Only a hash is stored server-side, so there is nothing to read back even in principle.
  • Never build a screen that displays the code to the customer, and never write code that expects to find it in a notification response — that field will never exist.

Retries mint a new code. If a delivery attempt fails and the order is dispatched again, or an operator resends the code, the customer receives a new code by SMS and the previous one immediately stops working. Two consequences for the UI:

  • Tell the customer to use the most recent SMS, not the first one. This is the single most common source of a failed handoff at the door.
  • A resend produces an SMS only — no new in-app notification. Do not poll the notification list to detect one; there will not be a second shipment_out_for_delivery row for the same dispatch.

Submitting a wrong code returns a generic 422 on the code field, with no hint about whether it was stale, mistyped or never valid. Repeated attempts are rate-limited per caller and per shipment, returning 429 — surface that as "too many attempts, wait a moment" rather than as a code error.

Implementation checklist

  • Add UI branches for shipment_ready_for_pickup, shipment_handed_to_post and shipment_out_for_delivery.
  • Keep the shipment_sent branch for historical rows; do not remove it.
  • Add a default branch that renders title + message for unknown types.
  • Move tracking-code display onto shipment_handed_to_post and read data.tracking_code defensively.
  • Show order_public_code to the customer, not order_id.
  • Build the admin recipient screen from GET / PUT /api/v1/admin/notifications/admin-order-paid-sms-recipients.
  • Gate that screen on the notification.admin-sms-recipients.manage permission from GET /api/v1/me.
  • Handle PUT 422 by keeping local state and highlighting errors["user_ids.{index}"].
  • Send {"user_ids": []} — not a skipped request — when the operator deselects everybody.
  • Flag admins with phone: null in the picker instead of silently letting them be selected.
  • Confirm nowhere in the codebase tries to read a delivery verification code from an API response.
  • Remove any UI that waits for a notification on picked_up — there is none.
