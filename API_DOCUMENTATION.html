Shop API

Complete API reference for frontend developers. Every endpoint is documented with realistic request bodies and full response shapes.

Base URL

http://localhost:8000/api/v1

All paths in this document are relative to this base.

Content-Type

Send Content-Type: application/json for every JSON request.

File upload endpoints use multipart/form-data.

Authentication

Protected routes require: Authorization: Bearer {token}

Response Format

All responses are JSON. Paginated lists include data, links, and meta keys.

Authentication Flow

This API uses split-auth onboarding: new users verify phone ownership via OTP first, while returning users may choose OTP or a password. The flow is:

  1. Call POST /auth/check-user with the phone number. The response tells you whether this is a new account and which methods are allowed: a new phone returns {is_new_user: true, allowed_methods: ["otp"]}; an existing phone that has set a password returns {is_new_user: false, allowed_methods: ["password", "otp"]}, while an existing phone with no password yet returns {is_new_user: false, allowed_methods: ["otp"]}. Render the login UI accordingly.
  2. OTP path: Call POST /otp/request with the phone â€” the server sends an OTP code (SMS in production, logged in development). Then call POST /otp/verify with the phone, code, and a device name to receive a Bearer token. Verify only proves phone ownership: capture the display name earlier via name/last_name on /otp/request, and add a password later via the authenticated POST /auth/set-password.
  3. Password path (returning users only): Call POST /auth/login-password with the phone and password to receive a Bearer token directly.
  4. Store the token and include it as Authorization: Bearer {token} on every subsequent protected request.
  5. The first time a phone number is used, an account is created automatically â€” register and login are the same flow.
  6. After verifying, check user.name === null in the response. If null, show a profile completion screen and call PATCH /profile before continuing into the app.
is_new_user flag: POST /otp/request returns is_new_user: true when the phone was not previously registered. Use this to show different UI before the OTP step â€” e.g. "Create account" vs "Welcome back" â€” or to decide whether to show a profile completion screen after verification.
OTP codes are single-use and expire in 2 minutes. Calling /otp/request again generates a fresh code and invalidates the previous one. A wrong guess does not burn the valid code â€” it remains usable until expiry.

Money & Prices

Important: All monetary values are stored and returned as plain integers in rials â€” the smallest currency unit. No floats, no currency symbols, no decimals. A product priced at 1,500,000 rials is returned as 1500000. Divide by 10 in your UI to display tomans.

Public Codes

Every entity a customer might read aloud, paste into a support ticket, or search for carries a short public code: a lowercase namespace + entity segment, a hyphen, and a six-character uppercase suffix.

bdp-K92XMQ    bdv-R7P4NZ    bdo-Q8M2XC    bdt-W4N7KP    bds-Z9C3TR    bda-H7Q9CM    bdc-T4K8NP

The bd namespace comes from the PUBLIC_CODE_NAMESPACE environment variable (required; normalized to lowercase). The suffix is drawn from a deliberately reduced, human-safe alphabet â€” 23456789ABCDEFGHJKMNPQRSTUVWXYZ â€” with 0, O, 1, I and L removed so a code cannot be misread into a different record.

Server-generated and immutable. Public codes are never accepted from client input, never appear as writable fields in create/update bodies, are never regenerated on update, and are never reused after a record is deleted. Sending uuid, sku, or public_code in a request body is silently ignored. Changing PUBLIC_CODE_NAMESPACE affects newly created records only â€” every stored code keeps the namespace it was issued under and stays valid forever.
Numeric IDs are unchanged. This is purely additive. Orders, Payments, Addresses and Categories keep their integer id, and every foreign key, relationship, checkout address_id, admin filter, internal contract, scheduled job, and gateway reference continues to use it. Public codes are for customer-facing display, search, support, and explicitly documented customer detail routes; they never replace structural numeric identifiers.
Older identifiers still work. Products created before this scheme keep their 7-character hexadecimal code (e.g. a3f9c1b) and their URLs still resolve; variants keep their earlier SKUs; shipments keep their SH-XXXXXXXXXX codes and remain addressable on every shipment route. Nothing was rewritten â€” only newly created records use the new format.

Searching by code

A search term that is a recognizable public code becomes an exact, indexed lookup rather than a substring scan. Input is trimmed and case-normalized, so BDO-q8m2xc finds bdo-Q8M2XC. Partial codes never match.

Media Upload Strategy

The API supports two ways to attach images to any entity that accepts one:

  • Pre-upload (recommended): Upload the file first via POST /media, receive a media_id, then pass that integer ID to the create/update endpoint as a plain JSON field. This is the cleanest flow for image pickers.
  • Inline upload: Send the image file directly in a multipart/form-data request to the create/update endpoint itself. Convenient for simple single-step forms.
These two approaches are mutually exclusive per field. Inline upload is available on category, gallery, and standalone variant endpoints (send media_id OR the file field, never both). Product create/update do NOT accept inline files â€” pre-upload via POST /media and pass primary_media_id / gallery_media_ids / variants.*.media_id.

This section walks through the complete frontend cart lifecycle from first visit to post-login merge. All examples use the native fetch API; adapt to Axios or any HTTP client as needed.

Step 1 â€” Guest browsing: create and persist a session

On a guest's first cart action, the server auto-generates a session ID and returns it as the X-Cart-Session-Id response header. Save it immediately â€” this is the guest's cart key for the entire browsing session.

async function guestCartRequest(method, path, body = null) {
  const sessionId = localStorage.getItem('cart_session_id');

  const headers = { 'Content-Type': 'application/json' };
  if (sessionId) headers['X-Session-Id'] = sessionId;

  const res = await fetch(`/api/v1/cart${path}`, {
    method,
    headers,
    body: body ? JSON.stringify(body) : undefined,
  });

  // Persist the session ID the server assigned (first request only)
  const returnedSession = res.headers.get('X-Cart-Session-Id');
  if (returnedSession) {
    localStorage.setItem('cart_session_id', returnedSession);
  }

  return res.json();
}

Step 3 â€” Post-login merge: combine the guest cart into the user cart

After a successful login, check whether a guest session existed. If it did, call the merge endpoint once, then clear the stored session ID. This is a fire-and-forget operation â€” if the guest cart is empty or the session ID is stale, the server handles it gracefully without error.

async function onLoginSuccess(token) {

  localStorage.setItem('auth_token', token);

  const sessionId = localStorage.getItem('cart_session_id');

  if (sessionId) {

      method: 'POST',
      headers: {
        'Content-Type':  'application/json',
        'Authorization': `Bearer ${token}`,

}

On logout, remove the token from storage. Do not create a new guest session proactively â€” let the next cart action trigger it naturally via the X-Cart-Session-Id response header.

Orders

The Order module converts the authenticated user's current cart into an immutable financial record. Every order creation is atomic: prices are snapshotted, inventory is reserved, and the cart is cleared â€” all in a single database transaction.

Authentication required. All order endpoints require Authorization: Bearer <token>. Unauthenticated requests return 401. Users without the order.create permission return 403.
Price snapshot. At checkout each item freezes: regular_price_per_unit (Catalog's regular price), automatic_discount_amount_per_unit and automatic_discount (the winning Promotion rule, or null), and price_per_unit â€” the effective price actually charged, before any order-level coupon. line_total is always price_per_unit Ã— quantity.

These integer-rial values are immutable: editing, expiring, or deleting the discount afterwards never changes a placed order, and the snapshot is self-contained so a historical line stays explainable without the live rule. The legacy compare_at_price field is retained for orders placed before promotions existed and is always null on new orders.
Customer & product snapshots. Orders are historical records, so every order carries a frozen copy of the buyer's identity and each purchased product. product_snapshot.image_url is the purchased variant image; product_snapshot.primary_image_url is the parent product's primary image. Both come from the enriched Cart item and are never refreshed from Catalog. Historical snapshots created before primary_image_url existed remain valid without that key. The shared OrderItemResource exposes these snapshots and the automatic-discount fields consistently in customer and admin Order detail responses.
15-minute checkout TTL. A pending order that is not paid within 15 minutes is automatically cancelled and its inventory reservations are released. If the user tries to check out again, the old pending order is cancelled and replaced by the new one.
Auto-cancel on re-checkout. If a user places a new order while a pending order already exists, the old pending order is cancelled (reservations released) and a new order is created in the same request â€” no manual cleanup needed.

Where order status actually changes (and why it's not here)

An order's status is a summary that the backend keeps in sync automatically. It moves forward as a side effect of two things:

  1. Payment â€” when a payment succeeds, the order becomes paid and a shipment record is created (see Payments).
  2. Fulfillment â€” the operator drives the parcel through the Shipment admin workflow (start-preparing â†’ hand-to-post / out-for-delivery / picked-up â€¦). Each shipment transition automatically syncs the order's summary status (processing â†’ shipped â†’ completed).

So if your admin UI needs a "mark this order as shipped" button, that button belongs on the Shipment screen and calls a Shipment admin action â€” never an Order endpoint. The Order detail here simply reflects the resulting status.

Mental model: Payment â†’ order paid â†’ shipment activated â†’ operator runs shipment actions â†’ order status auto-syncs. The admin Orders screen sits at the end of that chain as a viewer, plus a cancel escape hatch for orders that never got paid.

This walks the storefront checkout UI through choosing a fulfillment method and (for local delivery) a delivery session, placing the order, and rendering the shipment status afterwards. Step 1 â€” Let the user pick an address, then load methods

Call GET /shipment/methods with the selected address_id (omit it if none is chosen yet). Without an address the server returns only non-address-required methods (currently in-person pickup). Step 4 â€” Place the order and handle the "slot just filled" race

The availability list is a snapshot; between loading it and checking out, the last place in a slot can be taken. The server re-checks under a lock and returns 422 with errors.delivery_slot_id. Handle it by reloading slots and asking the user to pick again â€” don't treat it as a fatal error.

async function placeOrder(token, body) {
  const res = await fetch('/api/v1/orders', {
    method: 'POST',
    headers: { 'Content-Type': 'application/json', Authorization: `Bearer ${token}` },
    body: JSON.stringify(body),
  });

  if (res.status === 422) {
    const { errors } = await res.json();
    if (errors?.delivery_slot_id) {
      // Slot no longer available (or invalid) â€” refresh the slot picker.
      throw { type: 'slot_unavailable', errors };
    }
    throw { type: 'validation', errors }; // e.g. address_id ineligible, empty cart
  }

  return res.json(); // 201 â†’ the order, including shipment_method_code + shipment_snapshot
}
Don't cache the slot list across the payment step. If the user backs out and returns, reload /shipment/delivery-slots â€” capacity and availability change constantly.

Every product variant may configure max_quantity_per_order. Layer 1 â€” Automatic discounts

Always on, need no code, and apply per variant. A single variant may be matched by a variant rule, several product rules, several category rules (including ones aimed at an ancestor category), and several brand rules â€” all at once.

Automatic discounts never stack. Every matching rule is costed in rials and only the one producing the largest actual reduction is applied. The rest do nothing.

Worked example, base price 100,000,000:

RuleTargetConfiguredActual reductionOutcome
Phones Category Salecategory10%10,000,000loses

Specificity does not override savings. A 30% product rule beats a 20% variant rule, because the customer saves more. Specificity is only a tie-breaker: when two rules produce the exact same rial reduction the price is identical either way, and the winner is chosen deterministically by matched target (variant â†’ product â†’ category â†’ brand), then higher priority, then lowest discount id â€” so the rule recorded on an order is always reproducible.
Category discounts reach descendants. A rule aimed at Electronics also discounts a product filed under Electronics â†’ Phones â†’ Android.

Layer 2 â€” Coupons

A coupon is a marketing code the customer types. It does nothing at all until it is supplied â€” coupon-backed rules never affect the storefront, never appear in product responses, and never make a product "on sale".

  • One coupon per order, applied after automatic discounts.
  • Calculated on the post-automatic merchandise subtotal; shipping and tax are excluded.
  • Never allocated across items. A 100,000 coupon on a ten-item order does not put 10,000 on each line â€” it is recorded once at order level.
  • Codes are case-insensitive and whitespace-trimmed.

Flow: create the order â†’ check the coupon (advisory) â†’ initialize payment with coupon_code (authoritative, and freezes the price).

Order fields. Order responses carry coupon_code, coupon_discount_amount, coupon_snapshot (an immutable record readable without the live coupon), and payment_pricing_finalized_at. Before the first payment attempt these are null / 0 / null / null.

Customers can leave a comment on any product. Whether that same record also carries a star rating is decided by the server, from the customer's real purchase history â€” never by the client. Reviews â€” Frontend Implementation Guide

The flows below cover everything the frontend needs: composing a product page, writing/upgrading a review, handling the purchaser-only 422s, and running the moderation queue.

Flow 1 — Product page: show ratings and reviews together

A product page needs three independent pieces: the product (which already carries its synced rating_average/rating_count), the approved review list, and optionally the visitor's own review. None of these block each other — load them in parallel:

// Product payload already contains synced counters - no extra call needed:
//   { "rating_average": 4.5, "rating_count": 2, "product_id": 42, ... }
//   (rating_average null = not rated yet; product_id is the NUMERIC id reviews need)
const product = await fetch(`/api/v1/catalog/products/${slug}-or-code`).then(r => r.json());

// Approved reviews for the product (public, no auth). `subject_id` is the product's
// numeric id - take `product_id` from the product payload, never the public code.
const reviews = await fetch(
  `/api/v1/reviews?subject_type=product&subject_id=${product.product_id}&sort=highest`
).then(r => r.json());

// Render: star summary uses rating_average/rating_count from the PRODUCT payload;
// the list renders each review.body (+ gallery_urls, + seller_reply below it).
// Show a "verified buyer" chip when review.verified_purchase === true.
// rating === null means "comment without stars" - render it like a Q&A/note card,
// NOT as a zero-star review.
Do not compute averages client-side from the list. The list is paginated and approved-only, so a client-side mean would be wrong. The authoritative numbers live on the product payload and are updated hourly by the backend after moderation.
Moderation lag is expected. A freshly submitted review will not appear in the public list until an admin approves it (and re-approved after every edit). Set expectations in the UI ("your review is awaiting approval") instead of polling for it.

Flow 2 — Writing a review: one optimistic form, two server-owned outcomes

You cannot know whether the current user counts as a verified purchaser — that is resolved server-side from order history at the moment of submission. So build one form (stars optional-looking, comment required, photo picker) and let the 422 responses drive corrections:

async function saveReview(token, productId, { rating = null, body, galleryIds = [] }) {
  const res = await fetch('/api/v1/reviews', {
    method: 'POST',
    headers: { 'Content-Type': 'application/json', 'Authorization': `Bearer ${token}` },
    body: JSON.stringify({
      subject_type: 'product',
      subject_id: productId,          // numeric product id
      body,
      ...(rating !== null ? { rating } : {}),          // omit rather than send null
      ...(galleryIds.length ? { gallery_media_ids: galleryIds } : {}),
    }),
  });

  if (res.status === 201) return { outcome: 'created', review: await res.json() };
  if (res.status === 200) return { outcome: 'updated', review: await res.json() }; // same row edited

  if (res.status === 422) {
    const errors = (await res.json()).errors ?? {};
    // THE two purchaser-gating errors - handle explicitly, never generically:
    if (errors.rating)            return { outcome: 'needs-purchase', reason: 'rating' };
    if (errors.gallery_media_ids) return { outcome: 'needs-purchase', reason: 'photos' };
    return { outcome: 'invalid', errors };   // ordinary validation (missing body, etc.)
  }
  throw new Error(`Unexpected status ${res.status}`);
}

This needs zero special frontend code if you follow Flow 2 — but it explains what users experience. Someone leaves a comment (no purchase). Weeks later they buy the product and open "my review". They now add stars and photos to the same review via PATCH:

Flow 4 — Admin moderation queue

An operator UI is a three-state board over one endpoint pair. Poll (or refetch after each action):

// Worklist: everything waiting for a decision
const queue = await fetch('/api/v1/admin/reviews?status=pending', { headers }).then(r => r.json());

// Approve or reject - the SAME call, different body:
async function moderate(reviewCode, decision /* 'approved' | 'rejected' */) {
  const res = await fetch(`/api/v1/admin/reviews/${reviewCode}/status`, {
    method: 'PATCH',
    headers: { 'Content-Type': 'application/json', Authorization: `Bearer ${adminToken}` },
    body: JSON.stringify({ status: decision }),
  });
  if (res.status === 422) { /* status was not approved|rejected - bug in the UI */ }
  return res.ok;
}

// Optional seller reply (overwrites any previous one):
await fetch(`/api/v1/admin/reviews/${reviewCode}/reply`, {

  • Permissions: the queue needs review.view-admin, actions need review.moderate — admins have both, customers have neither, so hide the surface accordingly.
