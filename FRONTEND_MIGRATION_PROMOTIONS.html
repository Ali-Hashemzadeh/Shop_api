Frontend Migration Guide

Everything the frontend must change after the Promotion module landed — what to edit, where, and why.

One field was removed and nothing replaced it in place. compare_at_price is gone from every product, variant, and cart response. If your UI reads it to draw a strike-through price, that price will render as undefined/null until you switch to the new fields. This is the only hard break — start here.

What changed & impact

AreaChangeImpact
Products / variants compare_at_price removed → effective_price + discount added Breaking
Cart compare_at_price removed → effective_price, automatic_discount, regular_line_total, automatic_discount_amount added; cart totals gain regular_total_price, automatic_discount_total Breaking
Order items regular_price_per_unit, automatic_discount_amount_per_unit, automatic_discount added. compare_at_price kept but now always null on new orders Additive
Orders coupon_code, coupon_discount_amount, coupon_snapshot, payment_pricing_finalized_at added Additive
Coupons New POST /orders/{order}/coupon/check; coupon_code accepted on payment initialize New feature
Campaigns New public campaign list + campaign products endpoints New feature
Admin New /admin/promotions/* CRUD; compare_at_price removed from product/variant forms Breaking + New
Nothing else moved. Auth, addresses, shipment methods, delivery slots, inventory, media, and notifications are untouched. Product ids, SKUs, order public codes, and pagination envelopes are unchanged.

Breaking changes — do these first

1. Every variant object

Appears in: product detail, product lists, category products, campaign products, admin product list, variant endpoints.

{
  "id": 201,
  "sku": "bdv-K92XMQ",
  "type": "color",
  "is_default": true,
- "compare_at_price": 95000000,          <- REMOVED
  "base_price": 89000000,                // regular price (unchanged)
+ "effective_price": 71200000,           <- what the customer pays NOW
+ "discount": {                          <- null when nothing applies
+   "name": "Galaxy Launch Offer",
+   "type": "percentage",                 // or "fixed_amount"
+   "percentage_bps": 2000,               // 2000 = 20%  (null for fixed)
+   "fixed_amount": null,                 // rials       (null for percentage)
+   "amount": 17800000                    // actual rial reduction
+ },
  "max_quantity_per_order": 3,
  "attributes": { "color": "Black" },
  "image_url": null,
  "stock": 42,
  "effective_max_quantity": 3
}

Migration

// BEFORE
const price    = variant.compare_at_price ?? variant.base_price;
const wasPrice = variant.compare_at_price;
const onSale   = variant.compare_at_price > variant.base_price;

// AFTER
const price    = variant.effective_price;   // always present, always correct
const wasPrice = variant.base_price;        // show struck through only when discounted
const onSale   = variant.discount !== null;
const saved    = variant.discount?.amount ?? 0;
The semantics flipped. Previously base_price was the selling price and compare_at_price was the higher struck-through number. Now base_price is the higher regular price and effective_price is the lower selling price. If you swap the field names without swapping their roles you will show the discounted price struck through and display the full price as what the customer pays.

2. Every cart item

{
  "id": 55,
  "sku": "bdv-K92XMQ",
  "quantity": 2,
  "product_name": "Galaxy S25",
- "compare_at_price": 95000000,          <- REMOVED
  "base_price": 89000000,
+ "effective_price": 71200000,
+ "automatic_discount": { ... } | null,   <- same shape as variant.discount
  "line_total": 142400000,                // effective_price x quantity - PAYABLE
+ "regular_line_total": 178000000,       <- base_price x quantity (strike-through)
+ "automatic_discount_amount": 35600000, <- the difference
  "image_url": "...", "primary_image_url": "...",
  "available_stock": 42, "max_quantity_per_order": 3,
  "effective_max_quantity": 3, "remaining_addable_quantity": 1,
  "quantity_valid": true, "type": "color", "attributes": { ... }
}
line_total kept its name and its meaning — it is still the amount to charge for that line. It is simply now computed from effective_price. If you only ever rendered line_total and total_price, your cart already shows correct money; you just cannot show savings until you read the new fields.

3. Cart totals

{
  "item_count": 2,
  "total_quantity": 3,
  "total_price": 157400000,               // payable merchandise (unchanged meaning)
+ "regular_total_price": 193000000,      <- same basket at regular prices
+ "automatic_discount_total": 35600000,  <- total saved by automatic discounts
  "items": [ ... ]
}

Rules to internalize

1 · Never compute a price on the client

The server sends effective_price already computed with integer arithmetic. If you recompute it from percentage_bps you will eventually be off by a rial and disagree with the amount charged. Use percentage_bps for the badge text only (bps / 100 → 20%).

2 · Discounts never stack — show one badge

A variant has at most one discount object, never a list. Don't build UI that sums or lists multiple discounts per item.

3 · Prices are live until an order exists

Product and cart prices are recomputed on every request. A promotion can start or end between two page loads. Never cache prices across navigation, and always re-read the order response after checkout rather than assuming it matches the cart.

4 · All money is integer rials

Unchanged, but now applies to the new fields too. percentage_bps is not money — it is hundredths of a percent (2000 = 20%, 1250 = 12.5%).

Product list / grid

Endpoints: GET /api/v1/catalog/products, /categories/{id}/products, /catalog/campaigns/{slug}/products

Edit

  • Product card price → read the default variant's effective_price.
  • Strike-through price → render base_price only when discount !== null.
  • Discount badge → discount.percentage_bps / 100 + '%' for percentage rules, or format discount.amount for fixed ones.
  • Remove any "is on sale" logic comparing compare_at_price > base_price.

Filters — unchanged behaviour, one clarification

ParamBehaviour
has_discount=true|falseStill works. Now means "has an active automatic discount" instead of "has a compare-at price". Pagination is correct.
min_price, max_priceStill filter on base_price, not the discounted price.
sort=cheapest|most_expensiveStill sort by base_price.
Set expectations in the UI. A product discounted to 10,000,000 still sorts and filters by its 100,000,000 regular price. If your price-range slider implies otherwise, label it "regular price" — this was a deliberate scope decision, not an oversight.

Product detail

Endpoint: GET /api/v1/catalog/products/{uuid} — unchanged URL and shape apart from the variant fields.

  • Switching the selected variant must re-read effective_price / discount from that variant — different variants of one product can carry different discounts, or none.
  • "You save X" → discount.amount (already per unit).
  • Do not assume the default variant's discount applies to the others.

Cart

Endpoints: GET /cart, POST /cart/items (201), PATCH/DELETE /cart/items/{id}, POST /cart/merge

  • Line price → effective_price; line strike-through → regular_line_total.
  • Per-line savings → automatic_discount_amount; badge → automatic_discount.
  • Order summary "discount" row → automatic_discount_total; subtotal → total_price.
  • Guest and logged-in carts price identically — no user-specific automatic rules exist. No UI difference needed.
Do not add a coupon input to the cart. There is no coupon field on the cart and none will be added. Coupons attach to an order, so the input belongs on the payment step (see below). A cart-level coupon box would have nothing to call.

Checkout

Endpoint: POST /api/v1/orders — request body unchanged.

The order total can legitimately differ from the cart you just showed. Checkout re-reads live prices, so if a promotion ended seconds earlier the order is created at the new price. Render the totals from the order response, not from cart state you were holding. If you want to be friendly, diff them and warn the user before confirming payment.

New order fields at creation are always: coupon_code: null, coupon_discount_amount: 0, coupon_snapshot: null, payment_pricing_finalized_at: null.

Payment page & coupon input

Step 1 — Preview the coupon (optional, recommended)

POST /api/v1/orders/{order_id}/coupon/check     // numeric order id
Authorization: Bearer <token>

{ "code": "SUMMER10" }

// 200 OK
{
  "code": "SUMMER10",            // normalized (trimmed + uppercased)
  "discount_type": "percentage",
  "percentage_bps": 1000,
  "fixed_amount": null,
  "discount_amount": 18000000,
  "merchandise_subtotal": 180000000,
  "shipping_cost": 850000,
  "tax_amount": 0,
  "total_before_coupon": 180850000,
  "total_after_coupon": 162850000
}
  • Reserves nothing, changes nothing — safe to call on a debounced keystroke or an "Apply" click.
  • Requires login and order ownership. No special permission.
  • Errors are standard 422 validation on the code field — render errors.code[0].
Treat this as a preview, not a promise. Between check and pay the coupon can expire, be disabled, or have its last use taken by someone else. Always surface the result of step 2 as authoritative.

Step 2 — Pay, sending the code

POST /api/v1/payments/initialize

{
  "order_id": 42,
  "method_type": "online",        // or "in_person"
+ "coupon_code": "SUMMER10"       <- optional, NEW
}
Only ever send the code. coupon_discount_amount, final_total, and percentage are ignored if sent — the server computes everything. Never let the client propose an amount.

The freeze — the one behaviour that will bite you

The first successful call to /payments/initialize locks this order's pricing, including the decision to use no coupon.

Frozen asLater request sendsResult
SUMMER10nothingOK — reuses frozen pricing
SUMMER10summer10OK — case-insensitive
SUMMER10VIP20422
no couponnothingOK
no couponany code422

What to build

  • Read payment_pricing_finalized_at on the order. If it is not null, disable the coupon input and show the frozen coupon_code as read-only.
  • Retrying a failed payment: just re-post order_id + method_type. Do not re-send the coupon — omitting it is always safe and avoids any chance of a 422.
  • A failed gateway attempt does not release the coupon. The retry charges the identical amount. Don't prompt the user to re-enter a code after a failure.
  • If the user wants a different coupon after finalization, the only path is to cancel the order and start a new one. Say so plainly in the UI.

Order history & detail

Endpoints: GET /orders, GET /orders/{publicCode}, POST /orders/{id}/cancel, admin equivalents.

New order-level fields

{
  "total_amount": 162850000,
+ "coupon_code": "SUMMER10" | null,
+ "coupon_discount_amount": 18000000,
+ "coupon_snapshot": { ... } | null,        <- immutable historical record
+ "payment_pricing_finalized_at": "2026-08-08T19:41:09.000000Z" | null,
  "items": [ ... ]
}

New order-item fields

{
  "quantity": 2,
+ "regular_price_per_unit": 89000000,           <- strike-through
+ "automatic_discount_amount_per_unit": 17800000,
+ "automatic_discount": { ... } | null,         <- frozen snapshot
  "price_per_unit": 71200000,                     // charged (unchanged name)
  "compare_at_price": null,                       // LEGACY - see below
  "line_total": 142400000
}
compare_at_price on order items still exists — stop reading it anyway. It was kept so orders placed before this release keep rendering their historical value. Every new order writes null. Read regular_price_per_unit instead, which is populated for old and new orders alike (old rows were backfilled to equal price_per_unit).

Order summary block to build

Merchandise           sum(line_total)
Automatic savings     sum(automatic_discount_amount_per_unit x quantity)   // optional
Coupon (SUMMER10)    -coupon_discount_amount                              // when coupon_code !== null
Shipping             +shipping_cost
Tax                  +tax_amount
-----------------------------
Total                 total_amount

The coupon line is order-level only — it is deliberately never spread across items, so do not try to attribute it per line.

MethodEndpointReturns
GET/api/v1/catalog/campaignsVisible campaigns. ?landing=true → landing-page ones only
GET/api/v1/catalog/campaigns/{slug}One campaign, or 404
GET/api/v1/catalog/campaigns/{slug}/productsPaginated normal product objects
 
// GET /catalog/campaigns
{ "data": [ {
  "slug": "summer-sale",          // the public handle - use in routes
  "name": "Summer Sale",
  "description": "...",
  "starts_at": "2026-08-01T00:00:00.000000Z",
  "ends_at": "2026-09-01T00:00:00.000000Z"

Build

  • Landing-page section: GET /catalog/campaigns?landing=true, then link each to /campaigns/{slug}.
  • Campaign page: reuse your existing product grid component untouched — /campaigns/{slug}/products returns the same product shape and pagination envelope as /catalog/products, and supports the same page, per_page, sort, brand_id, category_id, min_price, max_price, search, available params.
  • Countdown timers can use ends_at (may be null = open-ended).
Don't assume every product in a campaign shares one discount. That is the whole point of campaigns — each product carries its own. Read each product's own discount. A product may even display a stronger discount that has nothing to do with the campaign; that is correct and intentional.
404 vs empty. An unknown/expired/inactive campaign → 404 (show a "campaign ended" page). A live campaign whose rules have all expired → 200 with an empty list (show an empty state, not an error).

  "max_discount_amount": 5000000,       // optional cap
  "starts_at": "2026-08-01 00:00:00",   // optional
  "ends_at":   "2026-09-01 00:00:00",   // optional, >= starts_at
  "is_active": true,
  "priority": 0,                        // tie-break only
  "targets": [
    { "target_type": "product",  "target_id": 15 },
    { "target_type": "variant",  "target_id": 91 },
    { "target_type": "category", "target_id": 7  },
    { "target_type": "brand",    "target_id": 4  }
  ]
}

UI notes

  • Percentage input: let the operator type 20 or 12.5 and send bps = value x 100. Never send a float. Max 10000 (100%).
  • Target pickers must call the existing Catalog admin APIs (products, variants, categories, brands) — the promotion API only stores raw ids and will happily accept an id that doesn't exist. Validate on your side; the backend deliberately won't.
  • Update semantics: omit targets to leave the reach untouched. Sending targets: [] on an automatic rule is a 422, not a "clear".
  • Delete returns 204 and is a soft delete — the rule stops pricing but history is kept. Label the button "Deactivate / Delete", not "Permanently delete".
  • Explain in the form that only the single best discount applies per variant — operators will otherwise expect stacking.

Admin — Coupons New

Base: /api/v1/admin/promotions/coupons

POST /api/v1/admin/promotions/coupons
{
  "discount_id": 12,              // MUST be a trigger_type=coupon, scope=all rule
  "code": "SUMMER10",             // A-Z 0-9 - _ only, max 32; auto-uppercased
  "is_active": true,
  "usage_limit": 500,             // null = unlimited
  "usage_limit_per_user": 1       // null = unlimited
}
  • The discount dropdown must be filtered to coupon-type rules only (GET /discounts?trigger_type=coupon) — picking an automatic rule is a 422.
  • Responses include used_count and remaining_uses — surface these in the list.
  • Renaming a code that already has redemptions is a 422. Disable the code field once used_count > 0.
  • Creating a coupon is a two-step flow for operators: create the coupon-type discount first, then the code. Consider a combined wizard.

Redemptions (read-only)

GET /api/v1/admin/promotions/redemptions — filters coupon_id, order_id, user_id, status. Statuses: reserved (claimed, awaiting payment), redeemed (paid), released (cancelled/expired, returned to the pool). Read-only — no edit/delete UI.

Read and write are separate: a user may hold promotion.view-admin and still get 403 on every mutation. Gate buttons individually, not the whole section.

Admin — Product & variant forms Breaking

  • Remove the compare_at_price input from: product create (nested variants[]), product update (nested variants[]), variant create, variant edit. The field is no longer accepted — sending it is silently ignored, so a leftover input looks like it saves and then vanishes.
  • Replace it with read-only text such as "Promotional pricing is managed under Promotions → Discounts." and a link.
  • The admin product list still supports has_discount; its meaning is now "has an active automatic discount".
  • Variant rows can show the live effective_price + discount so operators see the result of their rules without leaving the product screen.

Full checklist

Storefront — must do

  • Global search for compare_at_price and remove every read.
  • Product card / grid: price → effective_price, strike-through → base_price when discount !== null.

  • Send coupon_code on POST /payments/initialize.
  • Disable the coupon input when payment_pricing_finalized_at !== null.
  • Payment retry omits coupon_code.
  • Landing campaign section (?landing=true).
  • Campaign page reusing the product grid.

Admin

  • Remove compare_at_price from all four product/variant forms.
  • Discounts CRUD with the two-mode form.
  • Coupons CRUD with a coupon-rules-only discount picker.

  • Menu + button gating on the six permissions.

Gotchas & FAQ

"The price on the product page differs from my order." Expected if a promotion started or ended in between. Checkout re-reads live prices. Always show the order response's totals.
"Can I show two discounts on one product?" No. Only one automatic discount ever applies per variant. A coupon is separate and lives at order level only.
"Why is a 90%-off product not in my 0–20M price filter?" Price filters and sorts intentionally use the regular base_price. Label your filter accordingly.
"The coupon box returns 422 on retry." The order's pricing was already frozen with a different code (or none). Omit coupon_code on retries.
"A failed payment lost the customer's coupon." It didn't — a failed attempt keeps the reservation. Just retry; don't re-prompt.
"Are coupon codes case-sensitive?" No. They are trimmed and uppercased server-side; the response returns the normalized form, which is what you should display and store.
"Do customers need a promotion permission?" No. Browsing, campaigns, coupon check, and payment are protected by auth + ownership only. The six promotion.* permissions are admin-only.
Old orders. Orders placed before this release keep their historical compare_at_price value and have automatic_discount: null. Your order-detail UI must tolerate both shapes.
