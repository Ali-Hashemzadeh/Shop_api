Review Module

How product ratings and comments work inside the Shop API modular monolith — one entity that is always a comment and sometimes also a star rating.

What it is

Modules/Review owns exactly one entity: the Review. A review is a comment a signed-in customer leaves on a product. Whether that same row also carries a star rating is decided by the server, from the customer's purchase history — never by the client.

The module follows the standard Domain / Application / Infrastructure blueprint and obeys every enclosure rule of the monolith: no Catalog model is ever imported, no Order table is ever queried directly, and everything that crosses the wall travels as a contract call or an immutable DTO.

The mental model. A customer can always speak. They may only score if the backend can prove they bought the thing. And whatever they write goes back into the moderation queue.

One entity, two jobs

There is no separate comments table and no Comment model. A single reviews row holds:

Module boundaries

Review is a leaf consumer. Two contracts connect it to the rest of the system, and nothing else:

                    ┌────────────┐
                    │   Review   │
                    └─────┬──────┘
        asks "did user X buy product Y?"
                          │  OrderManagerInterface::hasPurchasedProduct()
                          ▼
                    ┌────────────┐          pushes absolute tallies hourly
                    │   Order    │   ┌────────────────────────────────────┐
                    └────────────┘   │ CatalogManagerInterface::         │
                                     │        syncRatingSummary()        │
                                     ▼                              │
                               ┌────────────┐                       │
                               │  Catalog   │◄──────────────────────┘
                               └────────────┘
                     reads reviews? NEVER. It stores counters only.
  • Order answers one question: hasPurchasedProduct(userId, productId) — true when at least one order item for that product sits on an order in a realized state (paid, processing, shipped). Cancelled, failed, and pending orders never grant rating privileges.
  • Catalog receives numbers, not queries: it stores raw rating_sum / rating_count on products and derives the average at read time. It cannot see the reviews table, and Review never sees products.
  • Media is asked about ids: gallery ids submitted by purchasers are validated against MediaManagerInterface; the DTO carries resolved public URLs, never raw ids.

Subject references: loose columns, not relations

Like media_id everywhere else in this codebase, the review's subject is stored as two plain columns: subject_type (an enum-backed whitelist) plus subject_id. There is deliberately no morphTo(): instantiating Catalog's Product model from Review would break the hard module-isolation rule, and an FK would weld the two schemas together.

The consequence is clean: consuming modules resolve their own subjects. Catalog enriches a page of products with one batch call — getSummaryForSubjects('product', $pageIds) — the same discipline as its batch stock lookup. Review's own public listing returns reviews only; composing them with product data is the caller's job.

Blog-ready without a migration. Adding blog-post reviews later means adding one enum case (blog_post) and teaching the Form Requests its verification rule. No schema change, no new string literals scattered through controllers.

Verified-purchase gating is validation, not a silent fix

The gating decision happens inside the Form Request, before any Action runs:

Nothing is silently dropped. A non-purchaser who submits a rating gets an explicit validation error on rating — the API never pretends the field wasn't there. Non-purchasers are allowed to speak; they just cannot score.

Purchase status is re-resolved on every write, including edits. That is what makes the upgrade path in the next section possible.

One review per user per subject

A unique index on (user_id, subject_type, subject_id) makes the write path an upsert. The classic flow:

  1. Before buying, the customer leaves a comment → row created, rating = null, verified_purchase = false.
  2. They buy the product (order reaches paid).
  3. They PATCH their review with a rating and photos → the same row is updated: verified_purchase flips to true, the rating sticks.
POST /api/v1/reviews            → 201 (fresh create)
POST /api/v1/reviews  (again)   → 200 (same row updated in place)
PATCH /api/v1/reviews/{uuid}    → 200 (owner-only edit)
Every edit resets status back to pending. An approved review that gets edited contains unmoderated content — it goes back to the queue, even if only a typo changed. The previous approval never leaks through.

The public listing serves approved rows only, always. Any status query parameter a client sends is ignored — there is no way to read pending or rejected content through the public route. The seller reply is a single overwritable field: replying again replaces it, no threads.

Rating sync to Catalog: the sales_count pattern

Averages are never computed live across the reviews table on product pages. Instead, an hourly scheduled command mirrors how best-seller counts already work:

  1. reviews:sync-product-ratings aggregates Review's own tables: rows with status = approved and a non-null rating, grouped per product → SUM(rating), COUNT(*).
  2. It pushes each absolute tally through CatalogManagerInterface::syncRatingSummary(productId, sum, count).
  3. Catalog stamps raw integers onto products.rating_sum / products.rating_count — the exact structural twin of sales_count.
Self-correcting sweep. Every product that has ever been reviewed (any status) appears in the sweep, so a product whose approved ratings all get rejected is synced back to zero without needing a global reset — review rows are never deleted, so the subject list is complete.

"4.5★ (2 ratings) · 3 reviews" is correct output

Because only rated rows feed the counters, the average and the review count answer different questions:

RowStatusFeeds average?Shown publicly?
"Great, 5★"approvedyes (sum+count)yes
"Great, 4★"approvedyes (sum+count)yes
"Question about sizing" (no rating)approvednoyes
"Terrible, 1★"pendingnono

Catalog derives rating_average = round(rating_sum / rating_count, 2) at read time — it is never stored, so it cannot drift from its inputs. Unrated products report null. The ordering math behind ?sort=rating and the min_rating filter is pure integer arithmetic ((rating_sum × 10000) / rating_count, rating_sum ≥ n × rating_count) — no floats touch the pipeline.

Authorization is permission-based throughout: roles are bundles, and ownership on PATCH is enforced by ReviewPolicy as a standard 403 — deliberately unlike the driver-API pattern where another driver gets a 404. An owner may always address their own review.

Deliberate non-goals

  • No separate Comment entity — one row is both rating and comment.
  • No blog support yet — the whitelist has exactly one value today.
  • No half-star or decimal ratings; integer 1–5 only.
  • No helpful/unhelpful voting, no reporting/flagging, no reply threads beyond the single seller reply.
  • No inline file uploads on review endpoints — media must be pre-uploaded via POST /api/v1/media.
  • No caching layer (matches Catalog's current state).
