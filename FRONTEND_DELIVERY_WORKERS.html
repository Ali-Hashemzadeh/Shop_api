Admin Frontend Guide

Delivery-worker accounts, shipment assignment, and the customer handoff code — what the admin panel must add, and why each rule exists.

Nothing existing breaks. Every change here is additive: new endpoints, new response fields, and one new precondition on a button you already have. If you ship nothing, the panel keeps working — except that “Mark out for delivery” and “Mark delivered” on local deliveries will start returning 422. Those two are the required work; everything else is new capability.

Breaking changes

Two, both on buttons that already exist, both scoped to local delivery only. Postal and pickup flows are untouched.

1. “Mark out for delivery” → 422 without an assigned driver

// POST /api/v1/admin/shipments/bds-K92XMQ/mark-out-for-delivery
// 422
{
  "message": "Assign a delivery worker before dispatching this shipment.",
  "errors": {
    "assigned_delivery_user_id": ["Assign a delivery worker before dispatching this shipment."]
  }
}

Fix: disable the dispatch button while assigned_delivery_user_id === null on a local_delivery shipment, and point the operator at the assign action. This applies to the retry path too — dispatching again after a failed attempt needs a driver just as much as the first attempt did.

2. “Mark delivered” → 422 without the customer’s code

// POST /api/v1/admin/shipments/bds-K92XMQ/mark-delivered   { "receiver_name": "Ali" }
// 422
{
  "message": "The delivery code is incorrect.",
  "errors": { "code": ["The delivery code is incorrect."] }
}

Fix: add a required code field to the completion dialog for method_type === "local_delivery". Leave the dialog exactly as it is for pickup (confirm-pickup) and postal (hand-to-post) — neither uses a code.

There is no admin override, and that is deliberate. An admin can complete a delivery they were never assigned to — but they still need the number the customer was texted. A code-free admin path would quietly undo the only thing the code proves: that somebody at the address actually received the parcel. If an operator is stuck, the answer is resend, not bypass.

Rules to internalize

A delivery worker is a shopper who also delivers

Drivers hold two roles: customer and delivery. They keep their own cart, orders and addresses. Never model “role” as a single-select on a user, never render “Delivery” as if it replaced “Customer”, and never send a request that would sync roles down to one.

Only shipments get assigned — and only local ones

Assignment lives on the shipment, not the order. Postal parcels are handed to a carrier and pickups are collected at the counter, so both reject assignment with a 422. Show the driver column and the assign action only when method_type === "local_delivery".

The code is never readable — only reissuable

Only a hash is stored server-side. No endpoint returns the code, and none ever will: not the admin shipment payload, not the shipment history, not the customer’s in-app notifications. Do not build a “show code” affordance, and do not put the code into any log, analytics event, or error report you forward.

A code belongs to one delivery attempt

Marking a delivery failed invalidates the code immediately. The next dispatch issues a new one and SMSes it. A code from a previous attempt will never work again — so if an operator is reading an old SMS thread over the phone, the correct action is to resend.

Reassignment does not change the customer’s code

Swapping drivers mid-delivery keeps the code the customer already has. The outgoing driver loses API access instantly; the incoming one is notified in-app and by SMS. Do not warn the operator that reassigning will invalidate anything — it does not.

Do not add a password field, and do not offer to generate one. The API issues no password and no temporary secret. The phone number is the credential: the new account signs in through the ordinary OTP flow and can set its own password afterwards from its own session. Copy for the success state should say something like “Ali can now sign in with 0912… using a one-time code.”
admin is not creatable here — sending it returns 422 on role. Do not put it in the dropdown “for completeness”; there is no admin-creation endpoint to fall back to.

Two permissions, not one

An operator holding only profile.create-any can create customers but gets 403 the moment they submit role: "delivery". Gate the option, not just the error: if the current user lacks profile.assign-delivery, hide or disable the “Delivery” choice rather than letting them fill in a form that cannot succeed.

User detail — grant the delivery role

post /api/v1/admin/users/{user}/delivery-role — permission profile.assign-delivery. Empty body.

POST /api/v1/admin/users/87/delivery-role      // no body

// 200
{ "message": "Delivery role granted successfully.", "data": { ..., "roles": ["customer", "delivery"] } }
  • Additive. Every role the user already had is preserved, and customer is ensured.
  • Idempotent. Clicking twice is harmless and returns the same 200 — no need to disable the button on an already-delivery user, though hiding it is tidier.
  • Phone required. A user with no phone gets 422 on phone: “A delivery worker must have a phone number.” Surface this next to the phone field and offer to edit the profile first — a courier with no number can neither receive an assignment SMS nor sign in.

There is no “revoke” endpoint in this release. If the panel needs one, it is a backend change, not something to fake by syncing roles from the client.

The snapshot is frozen at checkout by design: if the customer edits that address later, the delivery still points where it was ordered to.

Assign a driver

post /api/v1/admin/shipments/{publicCode}/assign-delivery — permission shipment.delivery.assign.

POST /api/v1/admin/shipments/bds-K92XMQ/assign-delivery
{ "delivery_user_id": 87 }

// 200 — the full shipment resource, with assignment fields updated

Use the same modal for assign and reassign; the API does not distinguish them. Pre-select the current assignee when there is one.

All rejections are 422 on delivery_user_id

MessageCausePrevent in UI by…
Only local delivery shipments can be assigned to a delivery worker.Postal or pickup shipmentHiding the action unless method_type === "local_delivery"

Reassigning to the same driver is a silent no-op. It returns 200, writes no history row, and sends no duplicate notification. You do not need to guard against it — but a toast saying “Assigned” when nothing changed reads oddly, so compare against the current value before showing a success message.

What the driver receives

On a real change of assignee the courier gets an in-app notification and an SMS containing the shipment code, order code and delivery window. They do not receive the customer’s address by SMS (they read it from their own app) and never the handoff code. Nothing for the admin panel to build — just useful when explaining the flow.

Dispatch

preparing→ ready_for_dispatch→ assign driver→ out_for_delivery→ delivered

Assignment can happen at any point before dispatch — the gate is only checked when the shipment moves into out_for_delivery. In practice the cleanest UX is to assign on the ready_for_dispatch screen and keep the dispatch button disabled until assigned_delivery_user_id !== null, with a tooltip explaining why.

The same gate applies to the retry path delivery_failed → out_for_delivery. If a driver was unassigned in between, the retry is blocked identically.

Dispatch is what issues the customer’s code and sends the SMS. After a successful dispatch, has_active_delivery_code flips to true — that is your cue to enable the resend action.

Mark delivered

post /api/v1/admin/shipments/{publicCode}/mark-delivered — permission shipment.delivery.complete.

POST /api/v1/admin/shipments/bds-K92XMQ/mark-delivered
{
  "code": "583241",            // required for local_delivery
  "receiver_name": "Sara Ahmadi",
  "note": "Delivered",
  "proof_media_id": 42
}

Everything downstream is unchanged and still automatic: delivered_at, the status history row, the order moving to completed, the delivery slot settling, and the customer’s “delivered” notification. You call one endpoint.

Input handling

  • Send the code as typed; the server strips spaces and dashes itself.
  • Do not validate the length client-side beyond a sane maxlength (16). Code length is configurable and telling a guesser their code was the wrong shape is already a hint.
  • Every failure — wrong, stale, from a previous attempt, never issued — returns the identical message. Do not try to differentiate them in copy; you cannot, and the API will not help you.
This endpoint is rate limited harder than the rest of the API. The delivery-confirm limiter allows ~5 attempts per minute per operator per shipment. On 429, read Retry-After and show a countdown rather than letting the operator hammer it. Note the budget is per shipment, so being throttled on one delivery does not block work on another.

Resend the code

post /api/v1/admin/shipments/{publicCode}/resend-delivery-code — permission shipment.delivery.resend-code. Empty body, returns the shipment resource.

Enable it only when method_type === "local_delivery" and status === "out_for_delivery"; anything else is a 422. It is SMS-only — no in-app notification is created, so the customer’s notification list will not show a duplicate “order sent” entry.

Resend replaces the code. There is no old plaintext to recover, so “resend” genuinely means “issue a new one and retire the old one”. Word the confirmation accordingly — something like “Send a new delivery code? The previous code will stop working.” Copy such as “resend the same code” would be wrong and would strand a customer who tries the old number.

Permission gating

GET /me now returns the caller’s effective permissions, so menu and button visibility should key off permissions.includes('shipment.delivery.assign') rather than roles.includes('admin'). Authorization on the server has always been permission-based — a permission can be granted to a non-admin operator, and a role check in the UI would hide a button that would in fact have worked.

// GET /api/v1/me
{
  "user": {
    "id": 1, "name": "Ops", "phone": "09197238119",
    "roles": ["admin"],
    "permissions": ["shipment.delivery.assign", "profile.create-any", ...]
  }
}

Error handling

StatusWhenUI response
401No/expired tokenExisting re-auth flow
403Missing permissionShould be unreachable if you gate on permissions. Generic “not allowed”
404Unknown shipment/user codeGeneric not-found
422Validation + every business rule aboveField-level errors; keys are delivery_user_id, assigned_delivery_user_id, code, phone, role
429Too many completion attemptsRead Retry-After, disable + count down

All 422 bodies use the standard Laravel shape — { message, errors: { field: [msg] } } — so your existing form-error adapter works unchanged. The only unusual key is assigned_delivery_user_id, which arrives on the dispatch request even though that request has no body; map it to a form-level banner rather than a field.

Driver app — separate surface, not the admin panel

Couriers must not be given the admin panel. They have no shipment.view-admin permission, so every /admin/shipments* call returns 403 for them. Their endpoints live under /api/v1/delivery/* and are scoped to their own assignments. Included here only so the boundary is clear — this is a separate build.
MethodEndpointNotes
get/delivery/shipmentsPaginated; optional status
get/delivery/shipments/{code}Address + map pin, slot, customer name/phone
post/delivery/shipments/{code}/mark-deliveredBody code (required), receiver_name, note

A shipment assigned to a different driver returns 404, not 403 — the two cases are deliberately indistinguishable. Do not write client code that treats 404 as “exists but forbidden”; from the driver’s side it simply is not there. The driver payload carries no order totals, coupon, or payment data at all.

Full checklist

Required — otherwise operators hit dead ends

  • Add a required code input to the “mark delivered” dialog for local_delivery
  • Disable “Mark out for delivery” while assigned_delivery_user_id === null on a local delivery
  • Handle 429 + Retry-After on the completion endpoint
  • Map the assigned_delivery_user_id 422 (from a body-less dispatch request) to a form-level banner

New capability

  • Users list: ?role= filter and roles[] chips
  • Reusable driver picker sourced from ?role=delivery
  • “Create user” form — customer/delivery only, no password field
  • Hide or disable the “Delivery” option without profile.assign-delivery
  • “Make delivery worker” action on user detail, with the no-phone 422 handled inline
  • Shipment list/detail: driver column + assigned-at, local deliveries only
  • Assign / reassign modal, hidden on postal, pickup, delivered and cancelled
  • “Resend code” button gated on out_for_delivery, with replace-not-repeat confirmation copy
  • Map link from address.latitude/longitude, rendered only when present
  • Switch menu/button gating from roles to permissions

Do not build

  • Any “show / reveal delivery code” affordance — the value does not exist server-side
  • A password or “generate temporary password” field on user creation
  • An admin option in the create-user role dropdown
  • An assign action on orders — assignment is on shipments
  • A single-select “role” control on a user

Gotchas & FAQ

“The driver says the code doesn’t work.”

Almost always a code from a previous attempt: marking a delivery failed retires the code immediately. Check has_active_delivery_code — if it is true, the customer has a valid code and is reading the wrong SMS; resend. If false, the shipment is not out for delivery.

“Can an admin just close the delivery?”

Yes, from any account with shipment.delivery.complete, and without being the assignee — but the code is still required. There is no bypass to build a button for.

“Why is the assign action missing on this shipment?”

It is postal or pickup, or already delivered/cancelled. All four are 422 server-side.

“Do I need to resend the code after reassigning?”

No. Reassignment keeps the customer’s code. Only a failed attempt or an explicit resend changes it.

“Where do I show the driver’s name?”

The shipment payload carries only assigned_delivery_user_id. Resolve it through the users endpoint — in practice, cache the ?role=delivery list you already load for the picker and look the id up locally.

“Why does a driver get a 404 instead of a 403?”

So that a shipment code cannot be probed for existence. Anything not assigned to the caller reads as nonexistent. This only affects the driver app; the admin panel sees everything it is permitted to.

“Is the customer’s address in the driver’s SMS?”

No — only the shipment code, order code and delivery window. The address lives behind the authenticated driver API.
